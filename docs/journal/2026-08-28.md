# 2026-08-28

## Fait

- **Diagnostic de l'import de production « invisible »**
  ([IFO-018](../tickets/IFO-018-import-annee-defaut-et-samedi.md)) : l'import du
  planning « LOCAUX XAVIER 26-27.xlsx » annonçait un succès mais le planning
  restait vide. Cause : en août, le sélecteur d'année scolaire proposait par
  défaut l'année *précédente* (`getMonth() >= 8`, mois indexés à 0 — le
  commentaire disait « past August », le code voulait dire septembre). Les 353
  attributions ont été créées du 24/08/**2025** au 24/06/**2026**. Confirmé par
  Thibault en prod (les cours sont bien là, en 2025). Diagnostic fait en
  simulant le parser PHP en Python sur le vrai fichier.
- **Correctifs** : défaut d'année corrigé (`>= 7`) ; le parser utilise désormais
  les vraies dates Excel du fichier quand elles existent (l'année du fichier
  prime sur celle du formulaire, qui ne reste qu'un repli pour les fichiers
  100 % texte) ; alerte rouge dans l'aperçu quand toute la période importée est
  déjà passée.
- **Feuille SAMEDI importée** : son en-tête ne contenait aucun des mots-clés
  matin/midi/soir, elle était ignorée en silence (sans perte aujourd'hui : elle
  ne contient que des locaux). « samedi » est maintenant reconnu comme bloc du
  matin (cours de 8h30 à 13h, confirmé par Thibault).
- **Rebondissement au test sur le vrai fichier** : les cellules de dates sont
  des *formules* (« =C2+7 »). Les recalculer avec PhpSpreadsheet est piégeux —
  le moteur évalue le texte « 24/08 » comme la division 24/8 et sort des dates
  en 1900. Le parser lit donc la **valeur mise en cache par Excel** dans le
  fichier (`getOldCalculatedValue()`), avec un garde-fou 2000–2100 avant
  d'ancrer une date. Vérifié dans le conteneur sur le fichier réel : 353
  attributions, 2026-08-24 → 2027-06-24, que l'on sélectionne 2025 ou 2026.
- 6 tests unitaires ajoutés sur le parser (fixture enrichie de deux helpers :
  « vraie date Excel » et « formule de date avec cache »).
- Vérifié dans le navigateur sur la stack dev : le sélecteur d'année propose
  bien « 2026–2027 » un 28 août.

## Reste côté prod

- Thibault purge les attributions fantômes 2025–2026 puis ré-importe après
  déploiement (la purge intégrée à l'import ne couvre que la plage du fichier,
  pas les fantômes d'un an en arrière).

## Leçon

- Tester sur le vrai fichier n'est pas optionnel : la première version du
  correctif « dates réelles prioritaires » passait tous les tests unitaires et
  aurait produit des dates en 1900 sur le fichier réel (formules recalculées au
  lieu du cache). Les fixtures reproduisent ce qu'on a compris du fichier, pas
  le fichier.
- Un import qui « réussit » avec des données invisibles est pire qu'une erreur :
  chaque écran de confirmation devrait confronter ce qu'il va faire à ce que
  l'utilisateur s'attend à voir (ici : la plage de dates vs aujourd'hui). Le
  fichier contenait la bonne année depuis le début — quand la source de vérité
  est dans les données, ne pas la redemander à l'humain.
