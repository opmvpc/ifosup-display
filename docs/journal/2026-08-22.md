## Résultats des audits

Verdict d'ensemble : **la reprise d'Opus est fiable** — détail dans
[IFO-013](../tickets/IFO-013-audit-croise-reprise.md) et les quatre rapports de
`docs/research/`.

- **Sécurité applicative (Fable)** — rien de bloquant. Deux points importants
  confirmés par relecture orchestrateur :
  1. `config/session.php:172` : `SESSION_SECURE_COOKIE` n'est définie nulle part et
     aucun trusted proxy n'est configuré dans `bootstrap/app.php` → le cookie de
     session part sans flag `Secure` derrière le proxy Coolify.
  2. `Admin/UserController::destroy()` : aucun garde-fou — un utilisateur peut
     supprimer son propre compte ou le dernier compte existant, or l'inscription et
     le reset par email sont désactivés → lockout complet du backoffice.
  Mineurs : `/screen/data` sans throttle, pas d'en-têtes de sécurité HTTP, import
  Excel DoS-able par fichier piégé (authentifié), sessions non invalidées au
  changement de mot de passe. Sain par ailleurs : pas de secret committé, `$fillable`
  stricts, pas de SQL brut injectable, pas de XSS, uploads validés.
- **Review des commits (Fable)** — chaque fix revendiqué vérifié réel à HEAD ; CI
  réellement verte (274 tests, 1094 assertions, PHP 8.4/8.5). Réserves mineures :
  `store`/`update` de créneau font un 500 (au lieu de 422) sur course résiduelle,
  compteurs de STATUS périmés d'une unité (corrigés ce jour).
- **Infra Docker/Coolify/CI (Opus)** — trois angles morts importants : **aucun
  `php.ini` actif dans l'image** (uploads plafonnés aux 2 Mo compilés de PHP, alors
  que les slides acceptent des vidéos de 300 Mo — la fonctionnalité était cassée en
  prod), pas de trusted proxies, logs applicatifs invisibles depuis Coolify
  (`LOG_CHANNEL=stack` vers un fichier sans rotation). Plus : conteneur en root,
  `migrate --force` sans verrou (sain à 1 replica), sonde MySQL aveugle à un
  `DB_PASSWORD` changé après coup, écarts de doc (port dev 8001, commande de dump,
  politique `ADMIN_PASSWORD` non appliquée par la commande).
- **Review croisée externe (Codex Sol)** — les meilleures prises de la session,
  toutes contre-vérifiées : la migration renommée par `073e159` casse la mise à
  niveau des bases pré-reprise (résurrection de `recurring_assignments`) ; la fusion
  de 3+ sections homonymes peut dupliquer des pivots `course_group` (l'agent Fable
  avait validé cette migration — la contre-lecture a tranché pour Sol) ; l'import
  est sensible à la casse là où MySQL ne l'est pas (500 / lignes ignorées,
  → [IFO-014](../tickets/IFO-014-import-sensible-casse.md)) ; MySQL local publié
  sur `0.0.0.0` avec identifiants connus ; nuance sur la sonde : retirer le mot de
  passe de la commande de healthcheck ne le retire pas de `Config.Env` dans
  `docker inspect` — la justification du 2026-08-21 était partiellement surévaluée.

## Correctifs appliqués dans la foulée

- `bootstrap/app.php` : `trustProxies(at: '*')` ; compose Coolify :
  `SESSION_SECURE_COOKIE=true` par défaut et `LOG_CHANNEL=stderr`.
- Garde-fous de suppression : impossible de supprimer son propre compte via
  `/admin/users` (la zone de danger affiche la raison), impossible de supprimer le
  dernier compte via la page profil. Tests ajoutés, test existant adapté.
- `Dockerfile` / `Dockerfile.dev` : `php.ini` production/development activé +
  `docker/php.ini` (upload 300 Mo, post 310 Mo, mémoire 512 Mo) ; healthcheck sur
  `/up` (ne crée plus une session en base toutes les 30 s).
- Migrations : garde anti-résurrection sur `create_recurring_assignments`
  (ancien nom déjà en table `migrations` → no-op) ; fusion `course_group` réécrite
  par insertion dédoublonnée.
- Stacks locales : ports MySQL liés à `127.0.0.1`.
- Docs : compteurs STATUS (274/1094, quatorze bugs), port dev 8001 dans README et
  CLAUDE.md, guide Coolify (dump via `MYSQL_ROOT_PASSWORD` dans le conteneur, gel de
  tous les mots de passe MySQL à l'init du volume, politique de mot de passe non
  appliquée par `app:create-admin-user`).

**À noter pour le prochain déploiement Coolify** : rien à changer dans l'interface
(les nouveaux défauts de compose suffisent), mais un redéploiement est nécessaire
pour reconstruire l'image (php.ini, healthcheck) et recharger l'environnement.

## Règles à retenir

- **Un seul auditeur ne suffit pas** : Fable a validé la migration de fusion que Sol
  a démontée ; la contre-lecture orchestrateur a départagé. Croiser puis vérifier
  soi-même reste la règle.
- **Un renommage de migration est une migration** : Laravel identifie par nom de
  fichier ; renommer = créer une « nouvelle » migration aux yeux des bases déjà
  passées.
- **Sans `php.ini`, PHP ment** : l'image officielle ne charge aucun ini ; les
  limites compilées (2 Mo) s'appliquent silencieusement et la validation Laravel ne
  voit jamais le fichier.
